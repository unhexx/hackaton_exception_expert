# Симуляционная валидация механики тестирования

Пакет проверяет на 500 синтетических кандидатах три механики теста:

- **текущую**: 3 вопроса, одинаковый ключ b-c-a, шаблон по номеру профиля;
- **новую v1**: банк семейств вопросов, индивидуальный вариант из 12 вопросов по единому плану, оценка уровня по IRT;
- **улучшенную v2** (`adaptive.py`): v1 плюс результат с уверенностью, дополнительные блоки у границы грейдов, накопление между попытками, вывод слабых тем по пилоту и осторожный порог.

Показатели соответствуют критерию оценки 2 ТЗ («Механика тестирования, валидация и категоризация») и итогам Q&A: точность, стабильность при пересдаче, разделяющая сила, устойчивость к уловкам и к утечке заданий.

Кабинет использует этот же код: `product/matching/assessment.py` собирает вариант и оценивает ответы функциями пакета (`form`, `irt`, `scoring`, `adaptive`) на банке в виде `bank.live_view` — 216 вопросов каталога в формате «оцените каждый вариант» (judge). Поэтому симуляция «v2 в кабинете» проверяет ровно то, что работает в продукте.

## Быстрый запуск

Все команды выполняются из корня репозитория (`C:\hackatone\spectrack`) с активированным `.venv` или через `.\.venv\Scripts\python.exe`.

```powershell
python -m product.validation_sim.generate   # банк, 500 кандидатов и пилот (data/)
python -m product.validation_sim.run        # прогон, отчёт и графики (out/)
python -m pytest product/tests/test_validation_sim.py -q
```

Чтобы получить график, нужен matplotlib. Это необязательная зависимость, в образ продукта он не входит:

```powershell
python -m pip install matplotlib
python -m product.validation_sim.plot       # перерисовать по готовому out/results.json
```

Прогон занимает около минуты на обычном CPU, GPU не нужен. Внешних зависимостей нет, только стандартная библиотека Python 3.10+.

## Файл кандидатов: как перенести в другую версию кода

Используйте `data/candidates.csv` (UTF-8 с BOM, открывается в Excel) или `data/candidates.json`. Файлы не ссылаются на таблицы проекта.

| Поле | Значение |
| --- | --- |
| `candidate_id` | `sim-0001` … `sim-0500`, стабильный ключ |
| `display_name`, `email` | Явно синтетические, домен `example.com` |
| `industry` | `it` |
| `specialization` | `backend`, `frontend`, `mobile`, `data`, `security` или `devops`, по 83–84 кандидата |
| `true_grade` | **Эталон**, истинный грейд. В продукте не показывать |
| `theta` | Истинный уровень на шкале `scale.py`, лежит внутри интервала `true_grade` |
| `declared_grade` | Грейд, на который кандидат заявился сам: 60% честно, 25% на ступень выше, 15% на ступень ниже |
| `team_role`, `work_format`, `stack` | Поля анкеты проекта. В CSV `stack` записан через `;` |
| `fsp_external_id` | Пусто: достижения ФСП в этом наборе не участвуют |

Распределение истинных грейдов: junior 35%, middle 30%, senior 22%, lead 13%.

Перенос в другую кодовую базу:

1. Скопируйте папку `validation_sim` целиком. Модули `scale`, `irt`, `bank`, `candidates`, `form`, `scoring`, `responders` и `simulate` работают без остального проекта; `bank.py` при этом построит банк без образцов текста.
2. `baseline.py` и проверка длины ответов используют `product.matching.grade`. Без него уберите блок `old` в `run.py`.
3. Если корневой пакет называется не `product`, замените префикс импортов `product.validation_sim` на свой.
4. Импорт кандидатов в кабинет: `email`, `specialization`, `declared_grade` (как `grade`), `team_role`, `work_format`, `stack` ложатся на поля профиля `PUT /api/candidate/profile`.

## Как устроена новая механика (кратко)

- **Семейство** — одна тема одной сложности с пятью равноценными вариантами-изоморфами. Сложность вариантов почти одинакова, поэтому варианты разные, а трудность у всех кандидатов одна (ТЗ §2).
- **План теста на грейд g:** 3 вопроса уровня g−1, 6 уровня g, 3 уровня g+1. Для junior и lead недостающие позиции добираются уровнем g.
- **Типы вопросов:** single (1 из 3), multi, order, numeric. Половина вопросов угадывается с вероятностью меньше 5%.
- **Ключ хранится только на сервере.** У вариантов ответа одноразовые id, порядок перемешан, «буквы правильного ответа» не существует.
- **Пересдача** подбирает другие семейства. Частота показов выравнивается по всему банку.
- **Решение по уровню θ (IRT).** θ не ниже границы следующего грейда даёт suggest_higher, не ниже границы заявленного даёт confirm, ниже даёт suggest_lower. Принудительного понижения нет (ТЗ §2).

## Механика v2 (`adaptive.py`)

Двенадцать вопросов дают погрешность уровня около ±0.4 при ширине грейда 1.2. Поэтому кандидат у самой границы грейдов иногда попадает в соседний грейд при любом тесте такой длины. v2 не пытается угадать грейд любой ценой. Тест честно говорит, насколько он уверен, и добирает информацию там, где она нужна.

1. **Результат с уверенностью.** Кроме грейда тест выдаёт вероятность того, что грейд верный, и положение кандидата внутри грейда (нижняя, средняя или верхняя треть). Статус «уверенно» ставится, если вероятность не ниже порога из пилота, иначе — «у границы». Это соответствует итогам совещания: неподтверждённое показывается со статусом, а не скрывается.
2. **Дополнительные блоки у границы.** Если после 12 вопросов вероятность по спорной границе лежит между 15% и 85%, кандидат получает 6 вопросов со сложностью именно этой границы, максимум два таких блока. Уверенные результаты заканчивают тест на 12 вопросах.
3. **Накопление.** Тест на грейд ниже или выше начинается не с нуля, а с уже известного распределения уровня. Грейд по-прежнему ставят только тесты.
4. **Пилот.** На отдельной группе (seed 7, не пересекается с 500 кандидатами) выводятся темы, которые плохо различают кандидатов: 61 из 285, корреляция с остальным тестом ниже 0.15. На той же группе выбирается порог «уверенно»: наименьший, при котором точность среди «уверенно» не ниже 93% + 1 п.п. запаса. Получилось 0.85.
5. **Осторожный порог.** Грейд присваивается, только если P(уровень ≥ граница) ≥ 60%. Завысить грейд хуже, чем занизить.

## Допущения и ограничения

- Ответы кандидатов смоделированы по IRT. «Настоящая» сложность вопроса отличается от записанной в банке (ошибка калибровки), поэтому оценка не идеальна.
- Параметры вопросов (a, b) заданы, а не получены по пилоту. В продукте их нужно уточнить по ответам первых кандидатов.
- Своих текстов у вариантов пока нет: `variants[].text = null`, кабинет показывает образец семейства (вопрос каталога). Длины вариантов ответа в каталоге выровнены: верный ответ самый длинный в 30% вопросов (было 58%). Последние 3 из 12 семейств каждой пары повторяют темы (`sample.reused = true`) — в кабинете они не показываются, их нужно дописать. После правки `product/matching/stems.py` пересоберите банк: `python -m product.validation_sim.generate`.
- Интервалы пересдачи по времени не моделируются.
- Точность среди «уверенно» опирается примерно на 250 решений и от прогона к прогону колеблется на ±1.5 п.п. Поэтому приводится среднее по 5 прогонам с разбросом.
- Порог «уверенно» подобран на пилотной группе, а не на тех 500 кандидатах, по которым считаются показатели.
- Утечка 50% банка означает утечку 720 вариантов вместе с ответами. Это крайний сценарий, и при нём защита слабеет. Поэтому банк нужно пополнять, а засвеченные варианты выводить из оборота.
