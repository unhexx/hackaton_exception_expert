# backend

Серверная часть прототипа: профили, мок достижений ФСП, категории как сохранённый факт, предложения работодателя, описание API.

## Вход

- `track/lct-fsp-vacancies/01-requirements.md` — разделы про приёмку, контракт ФСП, предложение.
- `track/lct-fsp-vacancies/roles/CONTRACT.md`
- Срез из `.agent/TODO.md`, который назвал product.

Модель данных в требованиях — гипотеза до спецификации ФСП. Менять имена полей можно в адаптере. Смысл (дисциплина, соревнование, результат, роль на старте, разряд как строка источника) сохраняется.

## Ход

1. Отделить клиент ФСП от остального кода. Сейчас реализация клиента читает мок. Позже туда встанет HTTP, не размазанный по ручкам кабинетов.
2. Разряд и место хранить как пришло. Функции «посчитать разряд по месту» в коде нет.
3. Категорию пишет matching. Backend сохраняет `category_id`, `rule_version`, `explanation` и отдаёт их в API. Сам правила не выдумывает.
4. Приглашение без обеих границ вилки, текста и названия компании не создаётся. Валюта только RUB.
5. Закрытый профиль не отдаёт работодателю достижения и контакты. Контакт — только после статуса `accepted`. Это проверка в тесте, не комментарий.
6. Каждый новый маршрут сразу попадает в OpenAPI: метод, путь, тело, ответ, пример. Форма документа — в требованиях.

## Не делать

- Не парсить внешние доски вакансий.
- Не поднимать продукт с хоста мимо compose из требований.
- Не вшивать токен боевой ФСП.
- Не верстать экраны. Контракт ответа согласовать с frontend одним примером JSON в документе API.
- Не помечать поля из резюме как подтверждённые ФСП.

## Стыки

Matching вызывает чистую функцию назначения категории и кладёт результат через API или общую таблицу, владельцем которой остаётся backend. Frontend не ходит в мок ФСП напрямую.
