# frontend

Веб-клиент двух кабинетов. Обратная механика должна читаться с экрана без устного пояснения: работодатель находит категорию и отправляет предложение, соискатель не рассылает отклики.

## Вход

- `track/lct-fsp-vacancies/01-requirements.md` — приёмка и демо-скрипт.
- Документ API, который приложил backend в `artifacts`.
- `track/lct-fsp-vacancies/roles/design.md`, если design уже сдал токены. Иначе нейтральная вёрстка с именами токенов из требований.

## Экраны MVP

Состав экранов — приёмка в требованиях. Не добавлять поля, которых там нет.

1. Кабинет соискателя: профиль, опрос, тест, блок достижений ФСП, категория и объяснение, входящие приглашения с диапазоном оплаты и кнопками принять или отклонить. Настройки публикации, согласие и ID ФСП — из требований, на экран их не выкидывать.
2. Кабинет работодателя: категории, карточки без контактов, форма приглашения. Кнопка не активна, пока диапазон, текст, компания или способ связи пустые.
3. Пустые состояния: нет достижений при живой категории, нет приглашений, тест ещё не сдан.

Чужой закрытый профиль не рисуется, даже если API по ошибке прислал лишнее: лишние поля достижений на карточке работодателя не показывать, пока в ответе нет признака открытости.

Подтверждённый факт и поле из резюме выглядят по-разному. Достаточно подписи «ФСП» и «из резюме».

## Не делать

- Не считать категорию на клиенте.
- Не ставить пакеты кабинета на хост. Кабинет открывается тем же compose, что в требованиях.
- Не подключать чужой UI-кит вместо токенов из требований. Файлы брендбука лежат в `brandbook-fsp/`.
- Не добавлять ленту вакансий и кнопку «откликнуться»: для MVP это вне скоупа.

## Готово

- Демо-скрипт проходится мышью по поднятому сервису.
- Проверены оба кабинета и профиль без достижений ФСП.
- `role=Coder`, `track_role=frontend`, `handoff_to=Tester`.

## Стыки

Если ответа API не хватает для объяснения категории или вилки, ход возвращается backend через `handoff_to=Coder` и `context_delta` с недостающим полем. Поле на клиенте не выдумывается.
